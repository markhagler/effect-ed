Lesson 4

Errors You Can See

The card says what can go wrong, so the compiler makes you deal with it. Effect also separates "problems we expected" from "the kitchen caught fire," and gives you tools like retry and timeout that snap onto any card.

The story

Two very different things can go wrong at the smoothie counter.

Out of mango. Annoying, but normal. It's going to happen sometimes. A good card lists it, and a good cook has a plan: offer strawberry.
Kitchen fire. Nobody writes "fire" on a smoothie card. It's not a smoothie problem, it's a bug in the building. You don't handle it with a strawberry.
Ty checks the card. If the error line still lists something nobody planned for, Ty stops it at the door. Add the plan, and the card is cleared.

Effect calls the first kind an error (expected, written on the card) and the second kind a defect (unexpected, a bug). The compiler makes you deal with errors. Defects crash loudly, which is what you want, because hiding a fire is worse than seeing it.

Name tags for errors

Each expected error gets a name tag so you can tell them apart:

import { Data } from "effect"

class OutOfMango extends Data.TaggedError("OutOfMango") {}
class BlenderJammed extends Data.TaggedError("BlenderJammed")<{ readonly speed: number }> {}

That's a whole error type. The string in quotes is the name tag. Now a card can list them:

import { Effect } from "effect"

const getMango = Effect.gen(function* () {
  if (Math.random() < 0.3) {
    return yield* Effect.fail(new OutOfMango())     // the "can go wrong" line
  }
  return "🥭"
})
// getMango : Effect<string, OutOfMango>
//                           ^ TypeScript figured this out on its own

Nobody wrote OutOfMango in the type. Ty read the recipe and filled in the "Can go wrong" line alone.

The picture: a card going through the kitchen

Catching one specific error

const getFruit = getMango.pipe(
  Effect.catchTag("OutOfMango", () => Effect.succeed("🍓"))
)
// getFruit : Effect<string>      <-- OutOfMango is GONE from the error line

Look at what happened to the type. Before: Effect<string, OutOfMango>. After: Effect<string>. Ty saw that we wrote a plan for OutOfMango and crossed it off the card. If a card still has errors on it when you reach Effect.runPromise, that's your reminder that you haven't planned for them.

Effect.catch (no tag) is the "catch anything on the error line" version. It still doesn't catch defects. Fires are not on the error line.

Two tools that snap onto any card

Because a card is just a plan, you can wrap a plan around a plan.

// Retry: "if it fails, try again, up to 3 more times."
const stubbornMango = Effect.retry(getMango, { times: 3 })

// Timeout: "give up if it takes longer than 2 seconds."  The error line grows:
const quickMango = Effect.timeout(getMango, "2 seconds")
// quickMango : Effect<string, OutOfMango | TimeoutError>

Try doing that to a Promise. You can't wrap a plan around a receipt, because the receipt already started.

Build the card, watch the error line

Snap tools onto getMango and watch the type change. Ty only lets a card through when its error line is empty.


  


  
Check yourself

  
1. "Out of mango" versus "kitchen fire": which one belongs on the recipe card, and why?Out of mango. It's expected and specific to this recipe, so the cook should have a plan. A fire is a bug in the building, not part of any recipe.

  
2. Before catchTag, the type was Effect<string, OutOfMango>. After, it was Effect<string>. Who crossed the error off, and how did they know they could?The type checker (Ty). It saw a handler for the exact name tag "OutOfMango," so that failure can no longer escape the card.

  
3. Why can you wrap retry around an Effect but not around a Promise?An Effect is a plan that hasn't started, so "do this plan again if it fails" makes sense. A Promise has already started; there's nothing to re-run.

  
4. Effect.timeout adds an error to the card. Is that a bad thing?No. It's honest. The card can now fail a new way, and the card says so.


  

    Teacher notes
    
    
      
  • The single most important moment in this unit is showing the error type disappear when you add catchTag. Do it live with hover-over types in the editor. Let them see the red squiggle when they forget.
    • 
      
  • Data.TaggedError("Name") makes a class with a _tag field. The _tag is literally the name tag. console.log(err._tag) proves it.
    • 
      
  • Defects come from throw inside plain code, or Effect.die. You can catch them with Effect.catchDefect, but that's for the fire-alarm layer of a program, not recipes.
    • 
      
  • Ask students to write the "Can go wrong" line for logging into a game: WrongPassword, ServerDown, TooManyAttempts. That makes it click that errors are a list of known things, not "stuff happened."
